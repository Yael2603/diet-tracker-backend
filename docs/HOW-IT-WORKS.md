# 🎤 איך השרת עובד: הסבר להצגת הפרויקט

המסמך הזה עוזר להבין ולהסביר את צד השרת. הוא עונה על ארבע שאלות:
**מה נשלח לשרת? מה חוזר מהשרת? איך המידע נשמר? איך עובדות ההתחברות וההרשאות?**

---

## 1. התמונה הגדולה

```
 [ דפדפן: React ]  ──בקשת HTTP + JSON──▶  [ שרת: Express ]  ──Prisma──▶  [ מסד נתונים: PostgreSQL ]
        ▲                                        │
        └──────────────── תשובת JSON ────────────┘
```

- **React (Client)**: מציג מסכים, ושולח בקשות לשרת לפי מה שהמשתמש עושה.
- **Express (Server)**: מקבל את הבקשה, בודק מי המשתמש ומה מותר לו, בודק שהנתונים תקינים, ומבצע את הפעולה.
- **Prisma**: ספרייה שמתרגמת קוד TypeScript לפקודות SQL מול מסד הנתונים.
- **PostgreSQL**: המקום שבו הנתונים נשמרים לתמיד. גם אחרי כיבוי השרת הם לא נמחקים.

שלושת החלקים רצים בענן: ה-React כ-Static Site, השרת ב-Render, ומסד הנתונים ב-Neon.

---

## 2. מה נשלח לשרת?

כל בקשה מורכבת מ:
| חלק | דוגמה | הסבר |
|---|---|---|
| **Method** | `POST` | סוג הפעולה: GET = קבלת מידע, POST = יצירה, PUT/PATCH = עדכון, DELETE = מחיקה |
| **URL** | `/api/weights` | על מה הפעולה |
| **Headers** | `Authorization: Bearer eyJ...` | ה-Token שמזהה את המשתמש |
| **Body** (ב-POST/PUT/PATCH) | `{ "date": "2026-10-22", "weightKg": 85.1 }` | הנתונים, בפורמט JSON |
| **Query** (ב-GET) | `?search=לחם&category=GRAINS` | חיפוש וסינון |

**דוגמה:** כשהמשתמש לוחץ "אכלתי ✓", React שולח:
```
POST /api/meals/from-menu
Authorization: Bearer eyJ...
{ "menuItemId": 20 }
```

## 3. מה קורה בתוך השרת? (המסלול של בקשה)

בכל מודול בתיקייה `src/modules` יש 4 קבצים. לכל קובץ תפקיד אחד:

```
בקשה ──▶ routes ──▶ middleware ──▶ controller ──▶ service ──▶ Prisma ──▶ מסד נתונים
```

| שלב | קובץ לדוגמה | מה הוא עושה |
|---|---|---|
| **Route** | `weights.routes.ts` | "טבלת הכתובות": איזו פונקציה מטפלת בכל כתובת |
| **Middleware** | `middleware/auth.ts` | בודק שיש Token תקין, ושלמשתמש מותר לבצע את הפעולה |
| **Controller** | `weights.controller.ts` | בודק את הנתונים שנשלחו מול הסכמה (Zod), וקורא ל-Service |
| **Schema** | `weights.schemas.ts` | הכללים לנתונים: למשל, המשקל חייב להיות בין 30 ל-300 |
| **Service** | `weights.service.ts` | הלוגיקה עצמה: בדיקת כפילות, שמירה במסד, חישובים |
| **Error Handler** | `middleware/error-handler.ts` | כל שגיאה בדרך מגיעה לכאן, והופכת לתשובה מסודרת |

**דוגמה: הוספת שקילה**
1. `weights.routes.ts`: הכתובת `POST /api/weights` מופנית ל-`controller.create`.
2. `authenticate` מוודא שיש Token, ו-`requireRole('USER')` מוודא שזה משתמש רגיל.
3. `controller.create` בודק את הגוף מול `weightSchema`. אם המשקל 5, מוחזרת שגיאה 400.
4. `service.createWeight` בודק שאין כבר שקילה באותו יום (אחרת 409), ושומר במסד.
5. השרת מחזיר **201** עם השקילה החדשה.

## 4. מה חוזר מהשרת?

- **בהצלחה**: JSON עם הנתונים, וקוד סטטוס: 200 (תקין), 201 (נוצר), 204 (נמחק).
- **בשגיאה**: תמיד אותו מבנה:
  ```json
  { "status": 400, "code": "VALIDATION_ERROR", "message": "הנתונים שנשלחו אינם תקינים",
    "details": [{ "field": "weightKg", "message": "הערך חייב להיות לפחות 30" }] }
  ```
- הסיסמה, או ה-Hash שלה, **לעולם לא חוזרות**. הקובץ `lib/presenters.ts` בוחר בדיוק אילו שדות יוצאים מהשרת.
- **השרת מחשב בעצמו**: קלוריות של ארוחה, סך יומי, ציון יומי, אחוז התקדמות ועמידה בתפריט. החישובים נמצאים בקובץ `lib/calculations.ts`.

## 5. איך המידע נשמר?

הטבלאות מוגדרות בקובץ `prisma/schema.prisma`. הפקודה `prisma migrate` יוצרת אותן במסד, לפי הקבצים בתיקייה `prisma/migrations`.

| טבלה | מה שומרת | קשרים |
|---|---|---|
| `users` | משתמשים (גם הדיאטן) | שייך למסלול אחד ולתפריט אחד |
| `tracks` | מסלולי דיאטה | לכל מסלול יש הרבה תפריטים |
| `menus` | תפריטים | שייך למסלול. יש לו הרבה פריטים |
| `menu_items` | פריט בתפריט: ארוחה, מאכל ומנות | שייך לתפריט ולמאכל |
| `foods` | מאגר המאכלים | |
| `weight_entries` | שקילות | שייך למשתמש. **שקילה אחת ליום** (אילוץ ייחודיות) |
| `meal_entries` | יומן אכילה | שייך למשתמש ולמאכל, ואולי גם לפריט בתפריט |
| `consultations` | פניות לדיאטן | שייך למשתמש |

**מושגים שכדאי להכיר:**
- **Primary Key (`id`)**: מספר ייחודי לכל שורה, שנוצר אוטומטית.
- **Foreign Key (למשל `userId`)**: מצביע על שורה בטבלה אחרת. כך יודעים למי שייכת כל שקילה.
- **Unique**: אסור שיהיו שתי שורות עם אותו ערך. למשל, אימייל.
- **"מחיקה רכה"**: מסלולים, תפריטים ומאכלים לא נמחקים, רק מקבלים `isActive=false`. כך ארוחות ישנות לא נשברות.
- **סיסמה**: נשמרת כ-**Hash** של bcrypt. זה "טביעת אצבע" שאי אפשר להפוך בחזרה לסיסמה.

## 6. איך עובדות ההתחברות וההרשאות?

### התחברות (Authentication: "מי את?")
1. המשתמש שולח אימייל וסיסמה ל-`POST /api/auth/login`.
2. השרת מוצא את המשתמש, ומשווה את הסיסמה ל-Hash באמצעות `bcrypt.compare`.
3. אם הסיסמה נכונה, השרת יוצר **JWT**: "כרטיס כניסה" חתום, שמכיל את מזהה המשתמש ותוקף של יום אחד. הקוד נמצא ב-`lib/auth-tokens.ts`.
4. React שומר את ה-Token, ושולח אותו בכל בקשה בכותרת `Authorization: Bearer ...`.
5. בכל בקשה, `authenticate` מאמת את החתימה בעזרת `JWT_SECRET`. רק השרת מכיר את הסוד, ולכן אי אפשר לזייף Token.

### הרשאות (Authorization: "מה מותר לך?")
- `requireRole('ADMIN')` מאפשר גישה רק לדיאטן, ו-`requireRole('USER')` רק למשתמש רגיל.
- **התפקיד נלקח ממסד הנתונים** בכל בקשה, ולא מהדפדפן. גם אם מישהו ישנה משהו בדפדפן, הוא לא יקבל הרשאות.
- **המשתמש המזוהה נקבע רק לפי ה-Token.** בבקשות לא שולחים `userId`, ולכן אי אפשר להתחזות למשתמש אחר.
- **בעלות**: בעריכת שקילה, השרת מחפש שקילה עם ה-id **וגם** עם ה-userId של המחובר. שקילה של מישהו אחר מחזירה 404.
- **שיתוף עם הדיאטן**: לפני שהדיאטן רואה שקילות או יומן, השרת בודק `shareWithDietitian`. אם השיתוף כבוי, מוחזרת שגיאה 403.
- **חסימה**: משתמש חסום (`isActive=false`) מקבל 403 מיד, גם אם יש לו Token בתוקף.

| קוד | מתי |
|---|---|
| **401** | אין Token, Token מזויף, או Token שפג תוקפו: "לא ידוע מי את" |
| **403** | יודעים מי את, אבל אסור לך: "אין הרשאה" |

## 7. שאלות שעשויות לעלות בהצגה

- **למה צריך גם שרת וגם מסד נתונים?** הדפדפן לא יכול לשמור מידע משותף ומאובטח. השרת שומר על הכללים ועל ההרשאות, והמסד שומר את המידע לתמיד.
- **למה הציון מחושב בשרת ולא ב-React?** כדי שהחישוב יהיה אחיד, ושאי אפשר יהיה "לרמות" מהדפדפן. גם הדיאטן רואה את אותו ציון בדיוק.
- **מה זה Swagger?** דף תיעוד אינטראקטיבי בכתובת `/api-docs`. אפשר לנסות בו כל קריאה בלי לכתוב קוד.
- **איך יודעים שהשרת עובד?** יש בדיקות אוטומטיות שבודקות התחברות, הרשאות, CRUD ופרטיות (`npm test`), ובנוסף כתובת `/api/health`.
- **מה זה Migration?** קובץ SQL שיוצר או משנה טבלאות. הוא מאפשר ליצור את אותו מבנה בדיוק בכל מסד נתונים חדש.
